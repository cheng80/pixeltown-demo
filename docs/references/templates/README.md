# 프로젝트 팀 문서 — 간소형(Lite)

> 초기 첨부 문서 템플릿이다. 현재 프로젝트 명세·현황은 [문서 안내](../../README.md)를 따른다. 아래 예시에서 `AGENTS.md`에 해당하는 원본은 실행 지시와 구분하기 위해 [AGENTS.template.md](AGENTS.template.md)로 보관했다. 자료 전체의 용도는 [개발 참고 자료](../README.md)에 정리했다.

개인~소규모 팀이 문서 유지비를 최소화할 때 사용하는 간소화 문서 세트다.

> 목적은 문서 수를 줄이는 것이 아니라, 적은 파일 안에서도 정본을 찾기 쉽게 만드는 것이다.

문서는 요약본이 아니다. 규칙, 예외, 수치, 명령, 체크리스트는 실제 작업에 쓸 수준으로 적는다. UI는 별도 파일을 만들지 않고 제품 명세의 화면 섹션에 둔다.

## 관리 원칙

- 이 폴더의 README, 명세, 현황, 작업 흐름이 사람이 관리하는 정본이다.
- `AGENTS.md`는 AI용 진입점이며 정본 내용을 반복하지 않는다.
- 문서가 복잡해져 한 사람이 찾기 어렵다면 파일을 임의로 늘리지 말고 Standard로 전환한다.
- 제목, 상태, ID와 링크는 사람이 빠르게 찾고 갱신할 수 있게 유지한다.

## 사용 방식

두 경로를 섞지 않는다.

- **신규 작성**: `PRODUCT_SPEC → TECH_SPEC → WORKFLOW → PROJECT_STATUS`. 완료는 이 문서 팩만으로 다음 작업자가 이어갈 수 있는가이다.
- **기존 문서 이관**: 옛 docs를 이 4개 문서로 재배치한다. 제목만 옮긴 요약본으로 완료하지 않는다. 기존 절차와 함께 검증 결과의 날짜·리비전·출처, 낡은 결과, 미완료·미실행 공백을 보존한다. 새 실험으로 공백을 채우는 일은 이관과 분리한다. 이관 전용 문서는 만들지 않고 README와 PROJECT_STATUS의 Handoff에 기록한다.

## 구조
```text
project/
├── AGENTS.md
└── docs/
    ├── README.md
    ├── 01_PRODUCT_SPEC.md
    ├── 02_TECH_SPEC.md
    ├── 03_PROJECT_STATUS.md
    ├── 04_WORKFLOW.md
    ├── plans/
    │   ├── PLAN_TEMPLATE.md
    │   └── PLAN-xxx.md       # 필요할 때만
    ├── decisions/
    │   └── ADR_TEMPLATE.md   # 필요할 때만
    └── assets/               # Optional. 실제 파일이 있을 때만
```

assets는 실제 파일이 있을 때만 만든다. 하위 폴더 이름은 프로젝트에 맞게 둔다. 빈 폴더로 구조를 맞추지 않는다.

## 핵심 경계
- `PRODUCT_SPEC`: 무엇을 왜 만드는가. 핵심 화면/상태도 여기 둔다.
- `TECH_SPEC`: 어떤 구조와 계약으로 만드는가.
- `PROJECT_STATUS`: 로드맵, 현재 작업, 진행 상태, 알려진 문제, 인수인계를 한곳에서 관리한다.
- `plans/PLAN-xxx`: 구현 전에 별도 설계가 필요한 기능/복합 작업에만 만든다.
- `WORKFLOW`: 팀의 작업·검증·문서 갱신 규칙.

인수인계는 `PROJECT_STATUS.md` 안의 섹션이다. 다만 내용은 전체 진행 복제가 아니라 바로 할 일, 변경된 계약, 검증 상태다.

## 정본 충돌 처리
```text
현재 실행 코드 + 테스트
        ↓
승인된 ADR / 현재 계약 문서
        ↓
제품 / 기술 명세
        ↓
프로젝트 현황 / 계획
        ↓
과거 문서 / Git history
```

충돌을 조용히 맞추지 않는다. 확정 불가면 `DOC-CODE-MISMATCH` / `NEEDS-DECISION`.

이관 시 README에 옛 파일 이름이 아니라 정보 이동 위치를 남긴다.

| 기존 정보 | 위치 |
|---|---|
| 제품 규칙 / 핵심 UI | `01_PRODUCT_SPEC.md` |
| 구조 / API | `02_TECH_SPEC.md` |
| 현재 상태 / 다음 작업 | `03_PROJECT_STATUS.md` |
| 작업 방식 | `04_WORKFLOW.md` |
| 상세 구현 계획 | `PLAN-xxx` |
| 중요 결정 | `ADR-xxx` |

## 문서 자산
폴더 이름은 달라도 된다. 맞출 것은 역할이다: 만든/검토한 디자인, 참고 자료, 실제 구현 화면, 제출 자산. 있는 것만 두고 섞지 않는다.

## 로드맵 → 계획 → 작업
간소형에서도 세 개념은 구분한다. 문서 수를 줄이기 위해 **로드맵과 작업은 `PROJECT_STATUS.md` 안에 두고, 계획만 필요할 때 별도 파일**로 만든다.

- 로드맵: 단계와 마일스톤. 상세 구현을 넣지 않는다.
- 계획: 기능·복합 작업의 구현 설계
- 작업: 바로 실행 가능한 작은 작업

오타, 작은 UI 수정, 단순 버그 수정에는 계획을 만들지 않는다. DB/API 변경, 여러 계층 변경, 큰 리팩터링, 복잡한 기능처럼 먼저 계획을 세울 가치가 있을 때만 생성한다.

## 팀이 문서를 사용하는 순서

프로젝트 이해: `README → PRODUCT_SPEC → TECH_SPEC → WORKFLOW`

작업 시작: `PROJECT_STATUS → 활성 PLAN(있으면) → 관련 Spec → 코드`

종료: `검증 → 계획/작업 상태 → 프로젝트 현황의 진행 상황/인수인계 갱신 → ADR(필요 시)`

AI의 읽기·갱신 순서는 `AGENTS.md`에만 둔다.
