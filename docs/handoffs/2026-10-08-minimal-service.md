# 미니멀 픽셀타운 인계와 향후 정리

갱신: 2026-10-08. 이 문서는 미니멀 게임의 배포 기반을 실 서비스 제작자에게 넘기기 위한 기록이다. 실 서비스 개발 완료나 출시 승인 문서가 아니다. 실제 검증 결과는 [PROJECT_STATUS](../03_PROJECT_STATUS.md)와 [worker 검증](../reviews/2026-10-08-worker-swap-verification.md)에 기록한다.

## 무엇을 만들고 있는가

메인 광장 하나에서 이동하고, 다른 사람을 보고, 별을 모아 저장하는 게임이다. 여기서 게임 로직을 바꿔도 접속과 플레이가 이어지는지 확인한다. 상점·꾸미기·펫·채팅·미니룸은 기존 게임에 남겨 두었다. 최소 게임의 계정과 별은 기존 게임과 별도다.

사용자가 여는 주소는 `https://pixeltown.fastmake.net`이다. 화면이 사용하는 백엔드만 새 주소로 바뀐다. 기존 게임을 열어 둔 탭은 기존 서버에 계속 연결된다. 첫 구조 도입은 기존 소켓을 새 서버로 옮기는 작업이 아니다. 도입 이후의 게임 worker 교체부터 연결을 유지한다.

## 실 서비스 제작 때 가져갈 부분

| 구성 | 재사용 이유 | 먼저 확인할 것 |
|---|---|---|
| `WorkerHost`, worker runtime | 연결과 게임 계산을 분리하고 최신 상태를 확인한 뒤 교체한다 | 새 게임 상태와 이벤트가 체크포인트·hash에 모두 포함되는지 |
| 버전별 release와 고정 링크 | 배포 파일을 완성한 뒤 한 번에 선택한다 | 상태·맵·입력 규칙이 호환되는지 |
| 단일 outbox·멱등 정산 | 후보 worker가 중복 지급하지 못한다 | 실 서비스 보상 규칙과 DB 제한 |
| `move`의 `seq/fix` | 예측 이동과 서버 보정이 교체 뒤에도 이어진다 | 새 입력 방식, 속도, 충돌 판정 |
| 장애 화면·독립 안내 | 실제 연결 장애 때 입력을 멈추고 안내한다 | 실 서비스 복구·재접속 정책 |

게임 worker 교체의 무중단과 접속 서버 자체의 무중단은 다르다. 현재는 접속 프로세스가 꺼지거나 Mac mini가 재부팅되면 연결이 끊긴다. 실 서비스에서 이 범위까지 유지하려면 별도 구조와 검증이 필요하다.

## 실 서비스에서 추가로 할 일

- 전체 게임 기능을 하나씩 붙이고, 해당 상태의 인계·정산·중복 처리까지 검증한다.
- 맵·속도·메시지·체크포인트 변경에 대한 버전 이행 방식을 정한다. 현재 교체는 같은 계약을 지키는 로직에 한정한다.
- 계정·원장 이전 여부를 별도로 결정한다. 최소 게임 DB를 기존 DB에 덮어쓰지 않는다.
- 다중 방·정원 초과·인터넷 지연·실제 기기·오랜 실행을 검증한다. 합성 사용자 100명은 실제 브라우저 100명과 다르다.
- 실 서비스 운영자 계정, 백업 복구, 모니터링, 부정 입력·가입 제한을 정한다.

| 시험 자료 | 로컬·최소 app의 `.test-work/` | 보고서와 백업을 보존한 뒤 시험 계정·토큰·자료를 별도 정리 |
| 문서 윤문 원본 | 로컬 `_workspace/` | 문서 검토가 끝난 뒤 필요 원본을 보관하고 정리 |

검증용 계정은 시험 자료의 사용자 ID 목록으로 식별한다. 원장이 있는 계정은 자동 삭제하지 않는다. 시험 계정 정리는 일반 사용자 데이터와 구분해 별도 지시와 보존 기준으로 처리한다. 기존 launchd·다른 게임·Oracle 작업·Cloudflare Tunnel 연결 자체는 이 작업의 정리 대상이 아니다.

## 작업을 이어받는 순서

1. `docs/03_PROJECT_STATUS.md` → `docs/plans/PLAN-007.md` → `docs/02_TECH_SPEC.md`를 읽는다.
2. [쉬운 구조 설명과 기술 문서](../architecture/zero-downtime.md), [구조 도식](../diagrams/worker-hot-swap.html), [프런트 계약](2026-10-08-worker-contract.md)을 확인한다.
3. health의 `hotSwap`, `workerDeployment`, `worker.revision/generation`, `persistence.pending/failed`를 확인한다. 실제 결과와 문서가 다르면 `DOC-CODE-MISMATCH`로 기록한다.
4. 화면 작업은 Claude 소유 범위를 지킨다. Codex 소유 `api.js`, `state.js`와 백엔드 계약 변경은 함께 확인한다.
5. 새 작업마다 변경 자원·검증·남은 일·정리 조건을 이 문서와 PROJECT_STATUS에 갱신한다. 계정·토큰·비밀번호는 기록하지 않는다.

## 운영 검사 재실행 조건

`tests/minimal-operational.mjs`는 최소 운영 서버의 합성 사용자 100명을 사용한다. 기존 게임에 사용하지 않는다. 실행 전에 승인·로비 정원·백업 위치를 확인한다. `tests/minimal-operational-control.mjs`를 최소 app의 `.test-work/operational-control.mjs`로 복사한 뒤 `MINIMAL_OPERATIONAL=1 MINIMAL_SOAK_MS=1800000 node tests/minimal-operational.mjs`로 실행한다. 최초 준비는 DB online 백업과 전용 계정 발급을 한다. 재실행할 때는 이전 private `accounts.json`을 `MINIMAL_OPERATIONAL_ACCOUNTS`로 지정해 중복 가입을 피한다. 토큰을 명령 인수·로그·문서에 넣지 않는다.

검사 중에는 로비가 100명으로 차므로 일반 입장이 거절될 수 있다. 검사는 별도 최소 서버에서 하고 기존 게임 서버에는 부하를 보내지 않는다. 성공/실패, 준비 단계 재시도, 실제 활동 시간, 교체 결과, 연결·보정·원장 대조를 모두 보고서에 남긴다. 두 실제 브라우저 검사는 합성 사용자 검사와 구분해 기록한다. 검사 완료 뒤에도 계정·자료는 보존하며 별도 정리 지시를 따른다.

배포 중 복구 주의: 고정 링크는 다음 후보를 가리킬 수 있다. 활성 worker 복구는 링크를 다시 읽지 않고 시작 때 확인한 검증 버전의 실제 파일 경로를 사용한다. 복구 상태는 마지막 확정 상태이며 과거 배포 체크포인트로 되돌리지 않는다. 이 구분을 실 서비스에서도 유지한다.
