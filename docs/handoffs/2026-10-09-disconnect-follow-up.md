# 접속 끊김과 화면 교체 후속 인계

2026-10-09 작성. [종류별 30분 검사](../reviews/2026-10-08-deployment-types-30min.md)는 완료됐지만 안정성은 실패했다. 검사 접속과 미니멀 game은 종료했고, 원본 worker·PB hooks·화면을 복구했다. 이 문서는 검사 종료 직후의 요청이다. 이후 사용자 승인으로 복구·heartbeat·입력 제한·화면 재시도를 구현했다. 최신 상태는 [복구 계약](2026-10-09-session-recovery-contract.md)과 [검증 보고서](../reviews/2026-10-09-disconnect-recovery.md)를 따른다. 운영 반영 완료를 뜻하지 않는다.

## 지금 확인된 범위

worker는 Colyseus 안에서 게임 계산을 맡는 스레드다. PB는 지갑·정산을 저장하는 별도 프로그램이다. 이번 worker/PB 교체 동안 Colyseus 접속 프로세스는 재시작하지 않았다. 현재 게임 소스 6개는 초기 구현과 같다.

그럼에도 배포 없는 단계에서 33건이 끊겼고, 전체 활동 중 SDK 256건·브라우저 2건이 끊겼다. SDK 244건은 서버 heartbeat 종료, 10건은 4002, 2건은 `CloudFlare WebSocket proxy restarting` 메시지가 있는 1001이었다. 각각의 원인과 복구 요구를 나눠야 한다. 원래 7건의 원인까지 확정된 것은 아니다.

## Codex 조사·구현 요청

1. **heartbeat가 어디에서 늦어지는지 확인한다.** ping 요청·실제 송신 완료·클라이언트 수신·pong 송신·서버 수신을 같은 소켓 ID로 잇는다. 압축 대기, 전송 큐, 이벤트 루프와 TCP/Cloudflare 경로 기록을 대조한다. 현재 terminate 호출자와 ping/pong 수는 있지만 패킷 구간별 기록은 없다. heartbeat 시간만 늘리는 것으로 원인 분석을 대신하지 않는다.
2. **4002 종료 경로를 확인한다.** close 호출자·종료 이유·직전 1초 메시지 수·seq 범위·수신 시각을 남긴다. 현재 제한은 120개/초다. 지연 뒤 정상 입력이 몰리는 경우와 실제 과다 송신을 비교하고, 필요한 경우 제한 정책과 입력 처리 방식을 함께 수정한다.
3. **미확인 입력을 대조한다.** SDK 최종 725개와 브라우저 198개는 미확인 수이며 유실 확정 수가 아니다. 재입장 전후 session/seq/fix와 서버가 처리한 입력을 확인한다. 재입장 때 pending을 비운 것을 무손실 성공으로 기록하지 않는다.
4. **화면 모듈의 재시도를 재현한다.** `minimal/game/src/visual-update.js`는 같은 `manifest.entry`로 동적 import를 다시 시도한다. 화면 코드 5회차는 첫 다운로드 실패 뒤 같은 주소에서 즉시 반복 실패했고, 다른 revision은 적용됐다. 일회성 다운로드 실패를 넣어 브라우저의 실패 캐시가 관여하는지 확인한다. 재시도 URL·검증·이전 화면 유지 정책을 함께 검토한다. 성공 수를 늘리려고 새로고침하거나 실패 수를 초기화하지 않는다.
5. **게시 도구 보완을 검토한다.** 검사 복제 앱에서만 HTTP 다운로드 최대 3회, 게시 Node의 주소별 연결 대기 250→2000ms를 적용했다. 상세 실패는 IPv4 ETIMEDOUT·IPv6 EHOSTUNREACH였다. main 도구에 옮길 때는 실패한 파일명·시도 수·원인 코드를 남기고, 원본 릴리스 보존·SHA 검증·게시 충돌 확인을 유지한다. 이후 성공만으로 이 설정이 원인을 해결했다고 단정하지 않는다.

추가 실험은 기존 왕복 이동/전체 맵 이동, 한 SDK 프로세스/분산 프로세스, 직접/공개 경로를 한 조건씩 바꿔 비교한다. 같은 틱·계정·서버 소스·관측 시간으로 맞춘다. 이번 검사 중 제품 소스는 변경하지 않았다.

## 외부 소켓 종료 뒤 복구 범위 — 결정 전 기록

Cloudflare가 기존 WebSocket을 닫으면 worker 교체 기능만으로 같은 소켓을 살릴 수 없다. **게임 계산 교체 중 접속 유지**와 **외부 접속 경로가 끊긴 뒤 상태 복구**는 별도 계약이다. 검사 당시 프런트의 `reconnection.maxRetries=0`, onDrop/onLeave/onError 또는 snapshot 8초 무응답 때 안내·입력 차단은 실제 장애를 드러낸다.

이 항목은 당시 NEEDS-DECISION이었다. 2026-10-09 사용자 요청으로 제한된 자동 복구를 구현하기로 결정했다. 아래 표는 구현 전 요청을 보존한 것이다. 자동 복구를 택한다면 Codex가 서버·`api.js`·`state.js` 계약을 먼저 확정하고, Claude가 그 계약에 맞춰 화면을 수정한다. 일반 worker/PB 배포를 재접속으로 처리할 이유는 없다.

| 항목 | 필요한 계약 |
|---|---|
| 시작 조건 | 외부 경로의 1001, 원인 불명의 1006, 실제 서버 종료를 어떻게 구분할지. 코드 1006 하나만으로 배포를 판정하지 않는다. |
| 서버 확인 | health/ready와 room 복구 가능 여부를 확인한다. 제한 시간·시도 횟수·복구 불가 응답을 정한다. |
| 게스트 | 같은 게스트 계정을 유지한다. 새 계정을 만들거나 별·지갑을 초기화하지 않는다. |
| 위치·진행 점수 | 서버가 마지막 확정 상태를 얼마 동안 보관하고 어떤 증명으로 이어줄지 정한다. 현재 새 입장 성공만으로 이전 위치 유지가 보장되는 것은 아니다. |
| seq/fix | 같은 세션 복구라면 서버의 확정 ack/fix부터 미확인 입력을 대조한다. 새 세션이라면 이전 seq와 섞지 않도록 세션 경계를 명시한다. 중복 입력·점수 반영을 막는다. |
| 입력·화면 | 복구 중 예측과 입력을 어느 범위까지 허용할지 정한다. 정상 배포에서 안내 화면·입력 차단이 나타나지 않는 요구를 유지하면서, 실제 장애를 얼마나 기다린 뒤 안내할지 정한다. |
| 실패 시 | 제한 시간 초과·방 소멸·인증 실패·비호환 버전에서 수동 재입장 안내로 전환한다. |

## Claude 인계 요청

- 화면 파일은 이번 Codex 검사에서 직접 고치지 않았다. 현재 장애 화면은 실제 끊김에 반응했다. 원인이 확인되지 않은 끊김을 숨기는 용도로 화면만 수정하지 않는다.
- 위 복구 계약이 확정되기 전에는 재연결 조건이나 seq/fix 처리 규칙을 화면 쪽에서 임의로 정하지 않는다. Codex가 `api.js`·`state.js`와 서버를 맡고, Claude는 안내 문구·표시 시점·입력 상태 표현을 맞춘다.
- 화면 업데이트 준비 실패는 연결 장애와 구분해 이전 화면을 유지한다. 반복 실패 이유와 적용된 revision을 확인할 수 있게 한다. `visual-update.js` 재시도 수정은 Codex와 계약을 맞춘 뒤 진행한다.
- 현재 타인 표시는 `playback.js`의 확인된 걸음 재생이다. 인계나 검증 결과에서 예전 100ms 보간으로 설명하지 않는다.

## 원문과 정리 대상

`.test-work/minimal-split-20261008/`에 최종 집계, 회차, SDK·브라우저·origin 사건, Postman 결과와 임시 실행 코드를 보존했다. 실제 SDK 자료 위치는 각 report.json의 observer 필드다. 원래 launchd plist는 보존했고 임시 계측 plist로 실행했다. PB hooks 확인용 API는 원본으로 복구했다.
