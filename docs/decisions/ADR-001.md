# ADR-001 — 서버 권한 게임과 원자적 결과·보상 저장

- 상태: 채택(현재 소스에 구현된 결정; 최종 실행 검증은 PROJECT_STATUS)
- 날짜: 2026-10-02
- 관련: FR-001/003/005/006, BR-001/003–007, PLAN-001

## 배경

클라이언트가 사용자 ID·위치·점수·보상을 직접 확정하면 다른 사용자 사칭과 결과 위조를 막기 어렵다. 라운드 결과와 인벤토리 보상을 독립적으로 저장하면 장애 중 일부만 남거나 재시도에서 중복 지급할 수 있다. 로컬 DB 중단과 게임 서버 재시작을 포함하는 데모 검증이 필요하다.

## 결정

1. Colyseus 입장마다 사용자 전용 PocketBase 클라이언트에 토큰을 넣고 `users.authRefresh()`로 실제 사용자 ID를 검증한다. 프로필도 사용자 권한으로 조회한다. 동시 사용자 사이에 authStore를 공유하지 않는다. 서버 저장용 관리자 클라이언트는 별도다.
2. 서버가 이동·충돌·시간·별 수집 거리·점수를 계산한다. 프런트엔드는 입력 방향과 별 ID를 요청하고 서버 snapshot을 그린다. 클라이언트가 보낸 좌표·점수를 결과 원장에 쓰지 않는다.
3. 종료 match를 디스크 outbox에 동기 쓰기·flush 후 rename하여 커밋하고 이후 종료 메시지를 전송한다. PB 저장 성공 전 outbox를 삭제하지 않는다. 재시작 시 기존 JSON을 읽어 재시도한다.
4. 게임 서버만 PB `POST /api/pixeltown/commit-match`를 호출한다. 훅은 superuser 인증을 요구하고 `$app.runInTransaction`으로 전체 참가자의 `results`와 `inventory`를 함께 처리한다.
5. 각 원장에 `(match_id,user)` unique index를 둔다. 동일 데이터 재전달은 성공으로 처리하고 점수·장소 또는 보상 수량·아이템이 다른 재전달은 거부한다. 참가자 중 하나라도 오류면 트랜잭션 전체를 rollback한다.
6. 일반 사용자는 자신의 원장을 읽고 서버만 쓰도록 collection rule을 잠근다. 저장 대기·재시도를 UI와 `/health`에 노출한다.

## 영향과 한계

PB 내부 결과·보상 쓰기는 원자적이다. outbox→PB 사이에는 분산 트랜잭션이 없으므로 최소 한 번 전달과 멱등성을 결합한다. PB 성공 후 outbox 삭제 전 재시작하더라도 같은 원장이 중복 생성되지 않는다. UI가 여러 collection을 따로 조회하는 순간의 시차는 있을 수 있으나 DB의 부분 커밋을 허용하는 설계는 아니다.

outbox 디스크 경로·PB 데이터·관리자 인증정보는 로컬 비공개 파일이다. 프로세스 재시작 복구는 해당 디스크가 유지된다는 전제이며 디스크 유실·다중 호스트 공유·진행 중 라운드 자체 복구를 보장하지 않는다. 잘못된 JSON·상충하는 결과는 자동 성공 처리하지 않고 pending으로 남을 수 있어 운영 확장 시 dead-letter·관찰 수단을 검토한다.

analysis.md의 원본 조사·관찰은 보존하며, 메인 담당이 자체 데모 기술 설명을 현재 트랜잭션 계약으로 갱신했다. 추가 문서 담당은 해당 파일을 편집하지 않는다. 실제 rollback·중복·장애 복구 검증 근거는 PROJECT_STATUS에 둔다.
