# ADR-006 — PB와 게임 접속 서버의 실행 서비스 분리

- 날짜: 2026-10-08
- 상태: 채택. 구현·로컬 검증·운영 서비스 분리·공개 경로 PB 코드 배포 확인 완료. 결과는 PROJECT_STATUS 7절 참조.
- 사용자 요청: PB 코드 변경 때도 이미 접속한 사람의 게임을 이어 갈 수 있도록 구현한다.

## 문제

PB와 Colyseus는 서로 다른 프로그램이지만 기존 최소 런처는 자식 하나가 종료되면 나머지도 종료했다. 이 때문에 PB 코드 배포로 게임 WebSocket·메모리 위치·진행 점수까지 잃을 수 있었다. 게임 worker 교체만으로는 이 실행 수명 문제를 해결할 수 없다.

## 결정

PB 전용 실행기와 게임 전용 실행기를 둔다. 운영에서는 서로 다른 launchd label로 관리한다. 로컬 `dev:all`도 실패한 구성만 복구한다. 사용자가 전체 개발 실행을 종료할 때만 게임 정산 후 PB를 종료한다.

PB가 응답하지 않아도 기존 접속자의 이동·별 획득은 살아 있는 Colyseus에서 처리한다. 정산은 기존 디스크 outbox에 남기고 PB 복구 후 재전송한다. 지갑은 마지막 확인값을 미확인으로 표시한다. PB가 필요한 신규 인증·입장은 일시 실패할 수 있다.

PB hooks 배포는 DB online 백업 후 PB만 종료하고 완성된 hooks로 교체한 뒤 PB만 시작한다. 코드 시작 실패는 이전 hooks로 복구한다. SQLite DB를 자동 복원하거나 같은 DB에 두 PB를 띄우지 않는다.

## 적용 조건과 한계

기존 통합 런처는 실행 중에 이 구조로 바뀌지 않는다. 최초 분리는 기본적으로 접속자 0명·정산 대기/실패 0/0에서 수행한다. 초기 끊김을 사용자가 허용한 경우 `--allow-connected`로 접속자 검사를 해제한다. 2026-10-08 운영 전환은 허용을 받고 실행했으며 실제 접속자는 0명이었다. 이후 PB 단독 배포부터 기존 연결 유지 대상이다. 호환되지 않는 DB 변경, PB 실행 파일 업그레이드, Colyseus 프로세스 교체, 호스트 재부팅은 별도 검증이 필요하다.

계약·명령·복구 한계는 [PB 배포 인계](../handoffs/2026-10-08-pb-deployment.md), 실제 실행 결과는 [PROJECT_STATUS](../03_PROJECT_STATUS.md)에 기록한다.
