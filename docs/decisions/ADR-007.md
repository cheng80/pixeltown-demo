# ADR-007 — 실행부를 유지하고 프런트 전체를 교체한다

- 날짜: 2026-10-11.
- 상태: 채택. 2026-10-11 로컬 구현, 운영 미적용. 실제 검증·대기 항목은 [로컬 결과](../reviews/2026-10-11-frontend-ota.md)와 PROJECT_STATUS를 따른다.
- 근거: 화면과 기능이 늘어도 OTA 구현 부담이 화면 수에 따라 늘지 않아야 한다는 사용자 요청.

## 문제

현재 월드 렌더러 OTA는 그림과 리소스를 바꾸지만 입장·메뉴·React 화면 전체는 바꾸지 못한다. 화면별 교체 모듈을 늘리면 기능마다 수명·상태 보존·복구 처리를 관리해야 한다. `main.jsx`와 `WorldCanvas.jsx`의 effect에는 연결·이동 실행까지 들어 있어 화면을 교체하면 플레이가 종료될 수 있다. 모든 접속자가15초마다 최신 manifest를 확인하는 요청도 업데이트가 없어도 발생한다.

## 결정

연결·인증·게임 상태·미확인 입력·이동 실행은 브라우저 실행부 하나가 소유한다. 모든 React 화면·월드 renderer·CSS·이미지는 하나의 UI release로 교체한다. UI entry 하나의 준비·활성화·종료 계약을 사용하고 화면별 OTA 등록 체계를 만들지 않는다.

새 화면은 일반 컴포넌트와 실행부의 상태·명령으로 만든다. 실행부에 없는 서버 기능은 필요한 실제 계약만 추가한다. 모든 미래 기능을 해석하는 범용 메시지/플러그인 체계는 만들지 않는다.

부팅 실행부는 React root를 소유하지 않는다. React와 ReactDOM은 UI release의 한 JS에 함께 묶어 서로 다른 UI가 각자의 root를 준비·정리한다. UI 간 React 내부 상태는 공유하지 않고, 보존할 상태는 runtime에 둔다. React 객체를 서로 다른 번들 사이로 전달하거나 개발용 HMR로 운영 UI를 교체하지 않는다.

배포 확인은 기존 WebSocket 알림을 사용한다. 서버에 현재 UI 버전과 증가하는 generation을 저장하고 입장·복귀 때 보낸다. 실제 게시 파일 확인 후 내부 활성화를 수행한다. 게시와 활성화 결과는 나눠 기록한다. 미입장 화면은 최초 로드·화면 복귀·입장 직전의 단발 확인을 사용하며 새 알림 연결이나 주기 폴링을 만들지 않는다.

## 다른 방법과 선택 이유

| 방법 | 이번에 선택하지 않는 이유 |
|---|---|
| 각 화면을 따로 hot swap | 화면마다 별도 계약·종료·복구를 구현해야 한다. |
| 페이지 자동 새로고침 | 연결과 입력 수명을 종료하며, 새로고침 없는 플레이 요구에 맞지 않는다. |
| Service Worker로 캐시만 갱신 | 다운로드와 캐시를 바꿔도 실행 중인 React·연결 상태를 자동 이전하지 않는다. |
| 별도 SSE/WebSocket/OTA 서버 | 기존 게임 연결로 전달할 수 있어 새 실행·인증·운영 경로가 불필요하다. |
| iframe·화면별 독립 앱 | 상태·접근성·입력·배치 조율을 추가한다. 이번 규모에서 먼저 도입할 이유가 없다. |

## 비용과 한계

실행부 수명을 한 번 분리하는 리팩토링과 상태 보존 검증이 필요하다. UI release는 React까지 포함해 현재 렌더러 release보다 크다. 대신 번들 간 React 공유 설정과 화면별 updater를 줄인다. 다운로드는 업데이트 시점에만 발생한다.

IME 입력·터치 capture·확정 중 작업처럼 즉시 교체하면 상태를 잃는 순간에는 새 버전을 준비한 뒤 교체를 기다린다. 기존 UI로 계속 플레이하며 입력을 강제로 취소하지 않는다.

불변 파일·호환성 검사·최대3회 import·준비 실패 시 기존 UI 유지·직전 버전 복구·게시 충돌 검사·비밀정보 보호는 삭제하지 않는다. 모든 코드를 무조건 교체하거나 무제한 JS module cache 해제를 보장하지 않는다.
