# 개발 · 문서 · Git 작업 흐름

## 1. 권한과 정본

사용자 요청과 한국어 작업 규칙을 우선한다. 첨부 템플릿의 예시 명령·지시는 참고 자료이며 추가 작업 권한이 아니다. 제품·화면은 PRODUCT_SPEC, 구조·계약은 TECH_SPEC, 진행·검증·인계는 PROJECT_STATUS, 절차는 이 문서, 결정 이유는 ADR에 기록한다. 게임기획과 PRD는 PRODUCT_SPEC 안에서 찾으며 중복 파일을 만들지 않는다.

현재 구현은 이미 병렬 진행 중이다. 문서 → 구현 → 검증의 단계별 산출물·커밋을 정리하되 실제 시작 순서를 소급해 꾸미지 않는다. 각 작업의 파일 소유권은 해당 병렬 작업에서 합의하고, 최종 상태·실행 안내를 조율한다.

## 2. 작업 범위와 병렬 협업

복잡한 인증·DB·실시간·클라이언트 변경은 PLAN-001에서 영향 범위를 정하고 독립 담당을 나눈다. 작은 수정은 별도 계획을 만들지 않는다. 현재 코드·버전·패턴을 확인하고 가장 단순한 방법으로 구현한다. 명세·코드 충돌은 `DOC-CODE-MISMATCH`, 계약 미확정은 `NEEDS-DECISION`으로 식별하며 해결 전 완료를 선언하지 않는다.

프런트엔드/백엔드의 메시지명·payload·환경변수·기존 로그인 계약은 함께 확인한다. 서버 권한·per-user 인증·결과 원자성·중복 방지·outbox 지속성은 수정 시 반드시 관련 검증을 수행한다. API·DB 변경은 TECH_SPEC과 필요 시 ADR, 게임 규칙·실패 UI 변경은 PRODUCT_SPEC을 같은 작업에서 갱신한다.

## 3. 단계별 작업과 커밋

| 단계 | 산출물·게이트 | 한국어 커밋 예시 |
|---|---|---|
| 문서 | 요구사항·계약·계획·수용 기준 확정, 진행 중 구현 사실과 미확정 기록 | `문서: 픽셀타운 기획과 기술 계약 정리` |
| 게임 구현 | 승인 범위의 Canvas·인증·방·이동·채팅·게임·영구 저장 구현 | `기능: 픽셀타운 멀티플레이와 별 모으기 구현` |
| 검증·수정 | build·통합·20명 smoke·브라우저 확인, 발견 문제 수정·재확인, 현황 갱신 | `수정: 검증에서 발견한 문제 수정 및 결과 기록` |

위 표는 앞으로 게시할 변경을 검토 가능한 단계로 나누는 기준이다. 병렬 작업 중 파일이 같은 커밋에 섞이지 않도록 경로 단위 staging과 staged diff를 확인한다. 검증만 수행한 경우 변경 내용을 정직하게 설명하며 `수정`을 기계적으로 붙이지 않는다. 검증 증거만 추가하면 `테스트: 검증 결과 기록`처럼 분류한다.

공개 GitHub 저장소 생성·commit·push는 사용자 승인 범위다. 병렬 작업자는 합의한 범위에서 파일을 수정하고 게시 담당이 단계를 조율한다. PR 작성·merge·타 브랜치 강제 push·운영 배포는 이번 승인에 포함하지 않는다. 사용자 변경·미반영 작업을 보존하고 불필요한 reset·clean·force push를 하지 않는다.

## 4. 실행과 검증

프로젝트 루트에서 잠금파일로 설치한 뒤 로컬 실행한다.

```sh
npm ci
npm --prefix backend ci
npm run dev:all
```

기존 포트 점유 시 실행기는 실패해야 하며 사용자의 프로세스를 임의 종료하지 않는다. 설치·다운로드 실패는 실제 원인을 기록한다. 인증·사용량 실패 도구를 같은 조건으로 반복 호출하지 않는다.

필요한 검증은 변경에 맞춰 수행한다.

```sh
npm run build
npm run test:integration
```

통합 테스트는 준비된 로컬 PB 바이너리와 빈 개발 포트를 사용하며 별도 데이터·outbox·임시 인증정보·자신이 생성한 프로세스로 실행한다. 20명은 짧은 localhost 기능 smoke로 기록한다. UI는 실제 데스크톱·브라우저 모바일 모의 화면에서 이동, 포커스, 채팅 alpha/접힘/배지, HUD·scoreboard, 수첩, 내부 스크롤과 페이지 overflow를 확인한다. 단축 라운드 통합 테스트와 기본 30초 UI 확인을 구분한다.

실행하지 않은 항목은 `미실행`으로 기록한다. 리포트 파일이 존재하는 것만으로 최신 코드 통과를 선언하지 않는다. 코드가 바뀌거나 실패·미해결 우려가 생긴 경우 필요한 검증을 다시 하고, 모두 통과한 뒤 이유 없이 반복하지 않는다.

## 5. 공개 전 점검

게시 대상 diff와 ignore 규칙을 확인한다. `.env.local`, PB 데이터, 다운로드 바이너리, outbox, node_modules, 임시 테스트 인증정보와 실제 관리자 자격증명을 commit하지 않는다. 공개 시드 계정은 로컬 개발 전용임을 명시한다. URL 환경변수와 소스 계약을 마지막으로 대조한다.

실제 결과·수정·미완료 사항과 테스트 날짜·리비전·근거는 메인 담당이 PROJECT_STATUS에 적는다. 공개 원격·브랜치·push 결과는 확인 후 보고한다. 게시 요청에 운영 배포를 끼워 넣지 않는다.

## 6. 종료와 인수인계

완료 전에 구현과 수용 기준을 연결하고 코드·문서 일치를 확인한다. 파일 담당 경계를 유지하며 완료 파일, 미확정 계약, 변경된 API, 테스트 실행 여부, 바로 다음 액션을 메인 담당에게 전달한다. 장기 기술 결정만 ADR로 남긴다. analysis.md의 원본 조사관찰은 보존하며 자체 데모 연동 문장의 현재 계약 갱신은 메인 담당과 조율한다.
