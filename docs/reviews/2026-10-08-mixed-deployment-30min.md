# 85명·30분·4종 배포 검사 결과

2026-10-08, Codex. **검사는 끝났지만 안정성 기준은 통과하지 못했다.** 실제 브라우저 1개는 연결과 이동을 유지했다. 합성 유저는 검사 중 32번 끊겼고, 종료 때 입력 804개의 처리 여부를 확인하지 못했다.

## 무엇을 검사했나

공개 주소 `https://pixeltown.fastmake.net`에서 SDK 합성 유저 85명과 Ego 브라우저 1개를 접속시켰다. 합성 유저 80명은 무작위로 이동하고 5명은 별을 따라갔다. 85명이 모두 연결된 **21:33:43.653 KST부터 22:03:44.036까지 30분 0.383초** 검사했다. 끊긴 합성 유저는 기존 검사 코드의 16초 대기 뒤 다시 입장했다. 이 대기는 제품 브라우저의 재연결 기능이 아니다.

3분마다 PB → worker → 리소스 → 화면 코드 순으로 교체했다. PB는 게스트·지갑·정산 API를 담당하고, worker는 이동·별·점수 계산을 담당한다. 화면 코드는 브라우저에서 그림을 그리는 렌더러다. WebSocket을 받는 Colyseus 접속 프로세스는 계속 실행했다. 그 프로세스 자체의 재시작이나 PB 실행 파일·DB 구조 변경을 검사한 것은 아니다.

PB에는 호환되는 확인용 API를 추가하고 복구했다. worker는 점수 합산의 같은 결과를 내는 소스 변경과 버전 주석으로 교체했다. 리소스는 CSS 색상과 SVG 파일, 화면 코드는 실제 렌더러 실행 여부를 확인하는 표시를 바꿨다. main의 화면 파일은 수정하지 않고 별도 복제 앱에서 빌드했다.

## 연결·동기화 결과

실제 브라우저는 같은 room/session을 유지했고 새로고침하지 않았다. 끊김·연결 오류·재입장 안내 노출은 모두 0건이었다. 화면 네 번 교체와 원본 복구 시에도 이동 키가 눌린 상태였다. 마지막에는 키를 해제하고 `seq=ack=49958`, `pending=0`, `fix=0`을 확인했다. 브라우저 계측 전체 구간의 snapshot 최대 간격은 237.9ms였다. 이 구간에는 입장 준비와 종료 정리도 포함된다.

공개 Postman 계약은 시작 전 4/4, 종료 직전 4/4을 통과했다. 화면 manifest·렌더러·CSS·글꼴·없는 파일 응답 계약도 종료 직전 5/5을 통과했다. 이 HTTP 검사 성공이 WebSocket 장시간 안정성을 의미하지는 않는다.

## 끊김에서 확인한 것

이번에는 서버 소켓별 ping/pong·종료 호출·대기열을 임시 기록했다. 전체 69건 중 68건, 검사 중 32건 중 **31건**에서 Colyseus `WebSocketTransport.mjs:166`의 heartbeat `terminate()`가 확인됐다. 해당 호출은 `pingCount=2`에서 발생했다. 쉽게 말하면 서버가 정해진 시간에 생존 응답을 받지 못했다고 판단해 연결을 닫았다.

끊김은 배포 후에만 발생하지 않았다. 활동 시작 후 첫 배포 전에도 12건이 발생했다. 활동 구간을 5분씩 나누면 15·9·4·2·1·1건으로 앞쪽에 몰렸다. 따라서 네 종류 배포가 증가의 단독 원인이라고 볼 수 없다. 이 분포만으로 입장 부하나 검사 도구가 원인이라고 확정할 수도 없다.

이것으로 **왜 pong이 늦거나 누락됐는지는 확정되지 않는다.** 클라이언트의 pong 송신 callback 성공은 서버 수신을 뜻하지 않는다. 일부 종료 시점에 압축 송신 대기열이 있었지만 다른 사례는 0이었다. 같은 서버의 실제 브라우저는 유지됐다. 한 Node 프로세스가 85개 SDK 연결을 처리하는 검사 방식, 압축·네트워크 경로·서버 처리의 영향을 나눠 확인해야 한다.

나머지 1건은 21:50:22.344 KST, bot 43, session `FHReHV2wl`이다. 서버의 ping/pong은 408/408이며 종료 직전 `pingCount=0`이었다. 서버 `terminate()` 호출 없이 양쪽에서 `1006`으로 닫혔다. 현재 기록으로 상대 클라이언트·Tunnel·중간 네트워크 중 누가 먼저 닫았는지는 구분할 수 없다.

후속 종류별 검사 준비 중 시각을 추가 대조했다. 활동 중 heartbeat 종료 31건 중 27건은 종료 전 1초 안에, 그중 24건은 100ms 안에 서버가 WebSocket 메시지를 받았다. 메시지 수신과 pong 미수신 판정이 겹쳤다는 증거다. 메시지 내용·유효성·이동 적용은 기록하지 않았으므로 처리 완료 증거는 아니다. 종료 시각과 lastMessageAt은 모두 같은 서버 로그에서 비교했다. 자료는 `.test-work/minimal-split-20261008/previous-heartbeat-message-age.json`이다.

원래 장시간 검사에서 나온 7건과 이번 69건은 별개 사건이다. 이번 heartbeat 기록을 원래 7건의 원인으로 대입하지 않는다. 서버 Node는 `24.21.0`, SDK는 `24.11.1`이다. 원래 서버의 Node 버전과 다르고 계측 부하도 있었다.

## 종료와 복구

합성 접속과 주기 배포를 종료했다. PB hooks는 백업과 같은 바이트로 복구했고 PB health는 200이다. worker 소스도 보관된 원본과 같으며 복구 후 generation 4, revision `0f9aad19`를 확인했다. 시작 시 실행 중이던 worker revision은 `82ffe0c3`였고, 종료 때는 기존 배포 검사 이전에 저장한 원본 소스로 되돌렸다.

공개 manifest와 실제 브라우저 모두 원래 화면 `c72da755`로 돌아왔다. 이 복구 과정에서 화면 준비 실패 수가 2에서 5로 늘어 자동 복구 검증은 실패했다. 마지막 사유는 `Visual preparation timed out`이다. 추가 3건 각각의 상세 이벤트는 저장하지 못했다. 최종적으로 원본이 적용된 것과 준비 단계 실패는 구분해 남겼다.

22:05:15.973 KST에 runner 종료를 기록했다. 이어 브라우저를 퇴장시키고 접속 0명·정산 대기/실패 0/0을 확인한 뒤 이번에 재개한 미니멀 게임 서비스를 종료했다. game 13620은 듣지 않으며 launchd label도 내려갔다. PB·Tunnel·기존 게임과 로컬 5270/18120/12620은 유지했다. 원래 LaunchAgents plist·main 화면 소스·다른 개발 세션은 변경하지 않았다. 이번 작업은 commit/push하지 않았다.
