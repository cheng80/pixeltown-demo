# 배포 종류별 30분 비교 검사

**검사는 끝났고, 접속·동기화 안정성 기준은 다섯 단계 모두 실패했다.** 2026-10-08~09 한국 시간 기준으로 각 30분, 총 활동 150분 1.154초를 검사했다. 2026-10-09 01:20:17 KST에 접속 정리와 게임 서버 종료를 마쳤다.

배포하지 않아도 SDK 끊김이 33건 발생했다. 현재 설치된 게임 로직 파일 6개는 초기 구현 commit `68d4ca8`과 같다. 따라서 “최근 로직 수정이 끊김 증가의 원인”이라고 결론 낼 근거는 없다. 같은 코드의 잠재 문제와 실행 환경·전송 경로·검사 조건 차이는 남아 있다. 과거 통과 기록도 해당 조건에서의 결과로 한정해야 한다.

- 화면 코드: 00:59–01:02 KST에 SDK 38건이 발생했고, 브라우저는 00:59:44.067에 끊겼다. 브라우저 origin 종료는 heartbeat, pings/pongs=941/939·송신 대기 0·마지막 메시지 이후 약 8초였다. 네 번째 배포 전에 발생했다. 해당 서버 이벤트 루프 최대 지연은 53.51ms, 수집한 서비스 로그에는 오류가 없었다. 게임·PB·Tunnel PID는 유지됐다.
- 리소스의 4002 10건: 00:31:49.863–00:31:52.873에 SDK와 origin이 모두 4002를 기록했다. 서버 maxMessagesPerSecond=120과 Colyseus의 제한 초과→4002 경로를 확인했다. 지연 입력이 몰려 제한에 걸렸다는 설명은 추정이다. 당시 메시지 수와 close 호출자 기록이 필요하다.

큰 끊김에서도 게임 서비스 재시작은 없었다. 교체 전후 시각만으로 worker 배포와의 인과를 확정하지 않는다. 이번 결과는 원래 개별 끊김 7건의 최초 원인 확정도 아니다.

## 화면 게시와 적용 실패

리소스 7회차는 기존 릴리스 목록 요청이 516ms 뒤 실패해 게시하지 못했다. 같은 회차를 별도로 다시 실행해 적용을 확인했다. 예정 HTTP 실패 1건은 유지했다. 리소스 9회와 원본 복구 동안 브라우저 끊김·화면 준비 실패는 0건이었다.

화면 코드 4·5회차도 목록/manifest 다운로드에서 게시 전에 실패했다. 4회차의 첫 별도 재시도는 publicRevision 요청에서 IPv4 ETIMEDOUT·IPv6 EHOSTUNREACH를 기록했다. SDK Node 24.11.1의 주소별 자동 연결 대기 기본값은 250ms였다. 게시 하위 프로세스만 2000ms로 조정하고 복제 앱의 다운로드를 최대 3회로 제한했다. 이후 게시가 완료됐지만 이것만으로 설정 변경이 원인 해결임을 입증하지는 않는다. SDK·게임 서버 설정은 유지했다. main의 게시 도구에는 이 임시 보완을 반영하지 않았다.

4회차 두 번째 재시도는 게시·적용됐다. 5회차 재시도는 게시됐으나 첫 동적 import 다운로드 오류 뒤 같은 URL 준비가 즉시 반복 실패해 적용하지 못했다. 이전 8회차 화면을 유지했고, 이후 다른 revision인 9회차는 적용됐다. 준비 실패 9건은 Style unavailable 1건과 5회차 모듈 오류 8건이다. 실패한 import의 브라우저 캐시가 관여했을 가능성은 별도 재현해야 한다.

브라우저가 이미 끊긴 뒤의 6~9회차와 4회차 재시도는 실제 revision 적용을 확인했어도 연결 유지 확인을 실패로 남겼다. 5회차는 적용 자체도 실패다. 관측 중 브라우저를 다시 입장시키거나 실패 수를 초기화하지 않았다. worker 종료 뒤 리소스 준비에서만 같은 TaskSpace로 재입장했다.

원본 화면 복구는 c72da755의 실제 적용을 확인했다. 연결은 이미 실패한 상태였으므로 복구를 연결 유지 성공으로 기록하지 않았다. cleanup의 visualFailuresDelta=9는 마지막 성공 시점 이후 누적 실패이며 원본 복구에서 새로 9건 발생했다는 뜻이 아니다.

## 과거 통과 결과와 달라진 조건

- 현재 simulation.js, simulation-worker.js, worker-host.js, worker-runtime.js, server.js, minimal/shared/world.js 6개는 초기 commit 68d4ca8·현재 main과 바이트 일치했다. 과거 통과 당시 바이너리·의존성·실행 옵션까지 같았다는 증거는 아니다.
- 초기 통과 검사는 별 추적 1명과 나머지의 12px 왕복 이동이었다. 전원 입장 뒤 입력을 시작했다. 현재는 별 추적 5명과 전체 맵 랜덤 이동 80명이며 순차 입장 중에도 먼저 입장한 봇이 움직인다. 전송량·압축 효과는 실제 대조 측정이 필요하다.
- 이번 SDK는 한 Node 24.11.1 프로세스이며 서버는 Node 24.21.0이다. 실제 브라우저 85개를 뜻하지 않는다. 모든 단계의 SDK 난수 seed=20261008·압축·계측 설정은 유지했다. 준비 때 난수를 이미 사용하고 별 위치·재접속이 달라지므로 같은 입력 경로를 그대로 재생한 것은 아니다.
- 순차 검사라 시각·네트워크·서버 누적 실행 시간과 준비 길이가 다르다. 기준 단계 중 HTTP 빌드 사전 확인도 있었고 첫 다운로드 timeout 뒤 보관 파일 캐시를 검증해 사용했다. 서버 소켓 계측 부하도 포함한다. 화면 코드 중 게시 도구 설정을 조정했으므로 게시 신뢰성 비교는 완전히 같은 조건이 아니다.
- 최초 브라우저 준비 실패와 합성 접속·배포 전 heartbeat 끊김은 setup-attempt-1 자료에 따로 보존했다. 완료 30분에 넣지 않았다.
